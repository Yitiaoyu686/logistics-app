# 空运业务流程：App vs Web 差异报告

> 2026-05-25 | 聚焦空运与海运差异，逐项对比

## 一、空运 vs 海运 核心概念差异

| 维度 | 海运 SEA | 空运 AIR |
|------|----------|----------|
| 运输单元名称 | 集装箱 | 集装号（板/箱） |
| 单元类型 | 20GP / 40GP / 40HQ / 45HQ | PALLET / BOX |
| 单元数量 | 1 JOB = 1 集装箱 | 1 JOB = N 个集装号 |
| 承运商 | 船公司 | 航空公司 |
| 运输单证 | 提单号(BL) + 船名航次 | 主运单号(MAWB) + 分运单号(HAWB) + 航班号 |
| 起运/目的 | 起运港 → 中转港 → 目的港 | 起飞机场 → 目的机场 |
| 装箱方式 | FCL整柜 / LCL拼箱 | 无此概念(按板计) |
| 铅封号 | 有 | 无 |
| 默认最大载重 | 26,000 kg | 1,500 kg (App) / 26,000 kg (Web, bug) |
| JOB前缀 | S-JOB... | A-JOB... |
| 服务类型 | 整柜/拼箱/普运 | 特快(3-5天)/普快(7-10天) |
| 运费单价 | ~12 CNY/kg | ~55 CNY/kg |
| 体积除数 | 5000 (1 CBM = 200kg) | 6000 (1 CBM = 167kg) |
| 入仓号 | 需要(集装箱入仓) | 不需要 |

## 二、装箱管理对比 (ContainerMgt ↔ packing + shipping-units)

这是海运与空运差异**最大**的页面。

### 2.1 页面对比总览

| Web ContainerMgt | App packing.tsx | 差异说明 |
|---|---|---|
| 单一组件,`isSea` 分支控制全部差异 | 单一组件,`job.business_line === 'AIR'` 分支 | 🟢 架构一致 |
| 统计卡片(5个) | ❌ 无统计 | 🔴 |
| 表格+行操作 | JobInfoCard + 扫码区 + 数据区 | 🟢 适配移动端 |

### 2.2 集装箱/集装号管理

| 操作 | Web SEA | Web AIR | App SEA | App AIR | 对齐 |
|---|---|---|---|---|---|
| **创建单元** | 单个:箱号+柜型+铅封+关联JOB | 批量:前缀+起始号+数量+打印Toggle | 单个:箱号+柜型+铅封+载重 | 批量:前缀+起始号+数量+打印Toggle | 🟢 |
| **单元列表显示** | 表格1列,首个集装箱,monospace | 表格多Tag,最多4个+溢出提示 | InfoCard单箱号 | 管理集装号链接→shipping-units | 🟢 |
| **添加订单** | 左侧Unit列表(SEA仅首个) | 左侧全Unit列表 | 扫码直接添加 | 扫码→需先激活集装号→双向扫描 | 🟡 |
| **执行出库** | 选择JOB+发往地址+拖车+司机 | 同SEA | 发往地址+拖车+司机 | 同SEA | 🟢 |
| **打印面单** | QRCode预览+打印按钮 | 同SEA | Label预览+打印N张 | 同SEA | 🟢 |
| **详情Drawer** | 单个集装箱+货物表 | Unit表+展开子行+利用率进度条 | ❌ 无独立详情 | ❌ 无独立详情 | 🔴 |

### 2.3 空运特有交互：双向扫码 (App only)

**App packing.tsx AIR mode 的智能扫描流程**（Web 没有此功能）:

```
扫码: 
  ├── 匹配到集装号 → 激活该集装号 → 自动绑定缓冲区所有待绑运单
  └── 匹配到运单号:
       ├── 已有激活集装号 → 直接绑定到该集装号
       └── 无激活集装号 → 进入"待绑缓冲区" → 等待后续扫集装号完成绑定
```

- 状态提示: "就绪" / "扫运单 → {active_unit}" / "已扫 N 单,扫集装号完成绑定"
- 600ms 防重扫
- 连续扫码 Toast 反馈(成功/警告/错误,2.5s自动消失)
- 手动输入Modal降级方案

**Web ContainerMgt AIR mode**: 通过 AddOrderDrawer 左侧Unit列表选择+右侧搜索添加，无双向扫描。

## 三、TMS 任务管理对比 (LegacyTaskManager)

|--------|----------|----------|

### 3.4 App端对比

App **没有** LegacyTaskManager。TMS操作角色(OPS_CN/OPS_US)在App不存在,因此:
- 🔴 所有任务创建/编辑/节点更新/成本录入 - App端均缺失
- 🔴 船务信息/航班信息的SEA/AIR差异化表单 - App端均缺失

App仅通过 `job-list.tsx` → `packing.tsx` 提供仓管视角的装箱操作。

## 四、订单创建对比 (OrderCreate)

### 4.1 SEA vs AIR 表单差异

| 维度 | Web OrderCreate | App order-create.tsx |
|------|----------------|---------------------|
| **业务线** | `resolvedTransportType` 从 businessMode 推得 | `businessLine` param 或 useBusinessLine() |
| **路由获取** | `systemApi.routes({ transportType })` | 使用 hardcoded 默认 routeCode |
| **服务类型** | 动态从 route 的服务类型过滤 | |
| SEA选项 | (从API动态) | FCL整柜 / LCL拼箱 / STANDARD普运 |
| AIR选项 | (从API动态) | EXPRESS特快(3-5天) / STANDARD普快(7-10天) |
| **默认服务类型** | LCL_SEA / STANDARD_AIR | FCL / EXPRESS |
| **入仓号** | 自动生成(入仓号字段始终显示) | **仅SEA生成**,AIR不生成 |
| **体积字段** | 始终显示 | **SEA非整柜时显示,AIR始终显示** |
| **运费预估** | 12 CNY/kg (SEA) / 55 CNY/kg (AIR) | 无实时计算(仅硬编码) |
| **重复下单检测** | 无 | 检测同收件人+同业务线订单 |
| **标题** | "创建订单" | **"海运下单" / "空运下单"** |

### 4.2 差异点

| 级别 | 差异 | 说明 |
|------|------|------|
| 🟢 | 服务类型 | 两端都根据业务线切换选项 |
| 🟢 | 入仓号 | 两端都是SEA有AIR无 |
| 🟢 | 标题 | 两端都显示当前业务线 |
| 🟡 | 运费预估 | Web从API获取,App无实时计算 |
| 🟡 | 路由数据 | Web从API动态加载,App硬编码 |
| 🟡 | 体积字段 | Web始终显示,App按模式+服务类型条件显示 |

## 五、运费试算对比 (Quote)

### 5.1 算法对比

| 参数 | Web PriceCalculator | App quote.tsx |
|------|-------------------|---------------|
| **数据来源** | `salesApi.quotes()` API调用 | 本地硬编码计算 |
| **路线选择** | 无(基于目的国) | 从API加载路线列表,选择具体路线 |
| **体积除数** | 未知(API计算) | SEA: 5000 / AIR: 6000 |
| **首重价格(≤1kg)** | 未知(API计算) | SEA: ¥63 / AIR: ¥120 |
| **续重价格(/kg)** | 未知(API计算) | SEA: ¥57 / AIR: ¥85 |
| **敏感货加价** | 未知(API计算) | 首重+20, 续重+20 |
| **结果显示** | 表格(渠道/时效/单价/总价) | 卡片(实重/体积重/计费重+明细+总价) |
| **分享功能** | 仅复制 | 复制 + 原生Share |

### 5.2 公式

```
体积重 = L × W × H ÷ (SEA: 5000 | AIR: 6000)
计费重 = max(实重, 体积重)
运费 = 首重价 + 续重价 × max(0, 计费重 - 1)
```

### 5.3 差异

| 级别 | 差异 |
|------|------|
| 🔴 | **数据源不同**: Web调API, App本地计算 → 价格可能不一致 |
| 🟢 | 算法逻辑一致(体积除数/首续重公式) |
| 🟢 | App多了路线选择和原生分享 |

## 八、空运特有数据差异（App 比 Web 多）

| # | 差异点 | 说明 |
|---|--------|------|
| 1 | **激活集装号机制** | App AIR有 activeUnit 概念，扫码时需先激活一个集装号才能绑定运单 |
| 2 | **待绑缓冲区** | App支持先扫运单后扫集装号的顺序，运单暂存缓冲区 |
| 3 | **双向扫码智能识别** | App自动区分扫码内容是运单号还是集装号 |
| 4 | **集装号搜索选择器** | App提供 UnitPicker Modal 作为扫码的降级方案 |
| 5 | **换下一个** | App在当前集装号完成后可快速切换到下一个 |

以上均为**App优于Web**的空运体验。

## 十、总体评估

### App 空运独特优势
1. **双向扫码**: 先扫运单或先扫集装号均可，智能识别+缓冲区
2. **连续扫码**: Toast反馈,不打断操作流,600ms防重
3. **空运定价**: 内置SEA/AIR双算法,可离线计算
4. **UI区分**: 海运绿色(#0F766E)、空运蓝色(#2563EB)色彩体系
5. **集装号管理**: shipping-units独立页面,批量创建+打印

### App 空运缺失（相对Web）
1. 🔴 无TMS操作(创建/编辑空运JOB,航班信息,MAWB/HAWB)
2. 🔴 无详情Drawer(空运Unit利用率进度条等)
3. 🔴 无统计卡片
4. 🔴 无费用报表(空运专属列隐藏逻辑)
5. 🟡 装箱无AddOrderDrawer(Web用左侧Unit列表+右侧搜索)

### Web 空运问题
1. 🔴 多个硬编码SEA导致AIR数据异常
2. 🔴 AirCargoMgt.tsx 导入但未使用(死代码)
3. 🟡 空运扫码体验不如App

### 对齐建议优先级
1. **P0**: 修复Web ContainerMgt硬编码bug
2. **P1**: Web端参考App双向扫码体验
3. **P2**: 删除或复活 AirCargoMgt.tsx
4. **P3**: App补齐TMS空运JOB创建(航班信息表单)
