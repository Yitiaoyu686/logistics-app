## 一、背景

### 1.1 起点问题

用户反馈"我的客户列表里有几条数据不完整"。逐层定位后发现的真实问题不止数据不完整：

1. **CRM 客户列表全部列空白**（除"国家"）—— `mapClient` 仅做了 `{...c}` 透传，前端 `Client` 期望 `shortCode/name/contact{}/totalOrders` 而后端返回 `customerCode/customerName/contactName/contactPhone/orderCount`，字段命名完全错位
2. **seed.ts 里的种子数据是"半成品"**：直接 `INSERT` 到表，跳过任何业务逻辑，导致：
   - `wms_stock` 有 8 条但 `wms_inbound_order = 0`（库存凭空出现）
   - `tms_job` 有 10 条但 `tms_job_order_rel = 0`（JOB 没绑任何子单）
   - `tms_tracking_event = 0`（节点历史全空）
   - `oms_package_actual = 0` / `pod_dpn_item = 0` / `fin_fee = 0` / `fin_payment = 0`（多张表全空）
3. **JOB 与订单的因果关系搞错了**：原以为是"客户→订单→入库→建 JOB"，实际业务是 **JOB 先订舱、后被订单装入**（订单入库后由仓管在"任务执行"页面装入对应 JOB）

### 1.2 用户的核心诉求

> "既然现在数据都是真实的了，你要按照整个系统的数据流转逻辑，创建一些真实的数据，你先梳理出数据流转的逻辑"

→ 不是拍脑袋造数据，而是**先把系统真实的数据流走清楚，再按流程产生数据**。

                              ├─ 海运: 1 个 shipping_unit (CONTAINER)

  → wms_stock.status = PACKED
  → sub_status = PACKED
  → unit.current_weight/volume 累加
  封箱:
  → unit_status = SEALED
  → job_status: PLANNED → LOADING

[7. 起运国办节点推进]
  tracking_event: 已离库→出口报关→海关查验→放行→已起运

  + 新 wms_stock（在到达仓）
  sub_status → PENDING_DELIVERY
  master.status → PENDING_DELIVERY

  分两支:
  ├─ 本站交付:  pod_dpn (DELIVERY) + pod_delivery_task / pod_pickup

### 3.2 海运 vs 空运的关键差异

| | 海运 | 空运 |
|---|---|---|
| JOB ↔ shipping_unit | 1 : 1 | 1 : N |
| unit_type | CONTAINER | PALLET |
| 节点流 | 12 节点（含海关查验） | 10 节点（少海关查验） |
| 关键节点 | 出口报关 → 海关查验 → 放行 → 已起运 | 出口报关 → 放行 → 航班起飞 |

## 八、附录：工程模式

本次新建的 5 个 repo 都遵循同一模式（**复刻 customerRepo**），值得固化为团队约定：

```ts
// xxxRepo.ts 模板
export interface XxxCreatePayload {
  // 与前端表单 + 业务对象对齐的字段，camelCase
  id?: string;          // 可选，方便 seed 控制
  // ...
  createdAt?: string;   // 可选，方便 seed 控制时间
}

export interface XxxCreateResult {
  id: string;
  // 业务编号 / 衍生数据
}

export function createXxx(db: Database.Database, payload: XxxCreatePayload): XxxCreateResult {
  // 1. 生成 id / 编号
  // 2. 主表 INSERT
  // 3. 子表 INSERT（包裹 / items / 关联表）
  // 4. 联动状态更新
  // 5. 返回 result
}
```

**好处**：
1. seed 和 routes/* 共用一套写入逻辑，避免数据形状脱节
2. 业务规则集中在 repo（如 `createInbound` 联动 sub/master 状态），调用方不用重复
3. 测试只需要测 repo，不用拉一个 Express
4. 未来如果要换 ORM 或换库，只动 repo 一层
