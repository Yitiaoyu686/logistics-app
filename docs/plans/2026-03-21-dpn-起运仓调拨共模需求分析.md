# 2026-03-21 DPN 与起运国仓调拨共模需求分析

## 1. 分析范围

- 范围仅包含 Web 端。
- 本文目标不是直接出实现方案，而是先明确业务口径：`DPN 管理`与`起运国仓储 -> 调拨记录`是否应按同一类业务对象来理解，以及起运国仓调拨记录需要朝什么方向改造。
- 结论基于三类证据：
  - 客户文档：`docs/meeting-notes.md`、`docs/excel-起运国仓.md`、`docs/excel-到达国仓.md`、`docs/excel-到达国办.md`
  - MCP 实页核查：2026-03-21 实际打开 Web 页面并查看列表/弹层
  - 当前实现：`client/src/pages/wms/origin/TransferList.tsx`、`client/src/pages/wms/destination/DPNManageList.tsx`、`server/src/routes/warehouse.ts`、`server/src/routes/v2.ts`、`server/src/routes/delivery.ts`、`server/src/database/schema.ts`

## 2. 先给结论

### 2.1 业务结论

- `DPN`在最新业务口径下，更接近“站点间调拨/调度单”，不是“末端配送单”本身。
- `配送`与`自提`属于货到目的仓后的末端交付方式；`DPN`负责站点到站点的中间运输管理。
- 因此，用户说“DPN 本质也是调拨”是成立的，且这一结论应优先于旧文档/旧代码里把 DPN 直接等同为 delivery 的口径。

### 2.2 对起运国仓调拨记录的需求判断

- 起运国仓的调拨记录不应继续停留在“简化仓间转移台账”层面，而应升级为与 DPN 同类的“调拨执行单”。
- 改造方向应是“业务共模”，即：
  - 统一调拨主对象的核心字段
  - 统一调拨的状态主链路
  - 统一调拨的装货/绑定/执行/到达/入库闭环
  - 保留起运侧与到达侧各自的扩展字段
- 现阶段不建议直接下结论说数据库一定要把 `transfer_orders` 与 `pod_dpn` 合并成一张表；需求层面先统一业务定义，技术合并放到下一阶段设计里确认。

### 3.3 当前实现证据

#### DPN 当前不是按“纯调拨单”实现，而是“DPN + delivery task”双实体

- `client/src/pages/wms/destination/DPNManageList.tsx` 中的核心状态是：
  - DPN 状态：`DRAFT`、`PENDING_ASSIGN`、`ASSIGNED`、`IN_TRANSIT`、`DELIVERED`、`SIGNED`、`CANCELLED`

  - `/pod/delivery-tasks` 是执行单
  - 创建执行单时会把 DPN 从 `PENDING_ASSIGN` 更新为 `ASSIGNED`

#### 起运调拨当前是通用 transfer 模型

- `client/src/pages/wms/origin/TransferList.tsx` 使用的状态是 `PENDING / IN_TRANSIT / ARRIVED / RECEIVED / CANCELLED`
- 其数据来自 `warehouseApi.listTransfers({ transferType: 'ORIGIN' })`
- `server/src/routes/warehouse.ts` 中 `transfer_orders` 的字段主要是：
  - `fromWarehouse`
  - `toWarehouse`
  - `businessLine`
  - `transferType`
  - `itemType`
  - `containerNo`
  - `totalPieces`
  - `totalWeight`
  - `totalVolume`
  - `status`
  - `reason`
  - `remark`

#### 数据库里当前有三套近邻模型并行

- `transfer_orders / transfer_items`
- 旧版 `delivery_orders / delivery_order_items`
- V2 `pod_dpn / pod_dpn_item / pod_delivery_task`

这说明当前系统在“调拨 / DPN / 配送”上确实存在并行建模，需求层面必须先定口径。

## 4. 冲突与取舍规则

### 4.1 冲突点

- 老文档与旧接口里，DPN 常被描述为“配送单”。
- 最新会议纪要又明确说：
  - DPN 负责站点间运输
  - DPN 与配送独立
- 当前真实页面中，DPN 页面展示的字段和动作，也更像“站点调拨执行单”，而不是“客户签收配送单”。

### 4.2 本次分析采用的取舍

- 优先级采用：`最新 meeting-notes` > `MCP 实页` > `旧接口命名/旧表结构`
- 因此本次需求分析认定：
  - `DPN = 目的仓侧的站点间调拨/调度单`
  - `Delivery = 末端配送单`
  - `Self Pickup = 自提单/自提流程`

## 5. 当前问题归纳

### 5.1 业务对象被拆散

- 起运仓调拨、到达仓调拨、DPN、配送，当前分别落在不同页面和不同接口模型里。
- 用户看到的是多个“看起来很像、但字段和状态又不完全一致”的对象。

### 5.2 起运仓调拨能力偏弱

- 当前起运仓调拨记录列表主要管理仓库来源、目标、装箱号、原因。
- 缺少 DPN 页面已经具备的：
  - 线路/JOB/订单维度可见性
  - 绑定运单能力
  - 执行人/司机信息
  - 打印
  - 物流状态与执行状态拆分展示

### 5.3 到达仓侧自身也重复

- 到达国仓储同时存在 `DPN管理` 和 `调拨记录` 两个页面。
- 其中 `DPN管理`已有真实数据与执行能力，`调拨记录`当前为空页面。
- 这说明系统已经出现“同一类业务在两个菜单下并存”的迹象。

### 5.4 状态语义不统一

- 起运调拨：`待发货 / 运输中 / 已到达 / 已入库`
- DPN：页面展示为`物流状态 + 执行状态`，底层却是 `DRAFT / PENDING_ASSIGN / ASSIGNED / IN_TRANSIT / SIGNED`
- 配送任务：又有一套 `ACCEPTED / SIGNED`

## 6. 需求口径建议

### 6.1 统一业务定义

建议把 `调拨`定义为统一业务对象：

- 定义：在组织/站点之间转移货物、集装号或订单集合的执行单
- 适用场景：
  - 起运国仓：卫星仓/分仓 -> 总仓，或总仓 -> 指定仓
  - 到达国仓：主仓 -> 分站/卫星站
  - 现有 DPN：到达站点间调度

### 6.2 DPN 在统一模型中的位置

- DPN 不再被定义为“配送单”
- DPN 应被定义为“目的仓侧调拨单”的业务别名或子类型
- 也就是说：
  - 从业务意义上，DPN 属于调拨
  - 从菜单语言上，可保留 `DPN管理` 名称，因为业务方已经熟悉这个词
  - 从系统建模上，应与调拨共用主链路

### 6.3 配送与自提的边界

- 货到目的仓后：
  - 如果走站点转运，用 DPN/调拨
  - 如果直接送客户，用 配送
  - 如果客户来取，用 自提
- DPN 完成后，不一定等于客户签收；它只表示站点间运输完成。

## 7. 起运国仓调拨记录的改造需求清单

## 7.1 菜单与职责

- 菜单仍放在 `起运国仓储 -> 调拨记录`
- 页面职责从“仓间转移列表”升级为“起运侧调拨执行管理”
- 保持与 `到达国仓储 -> DPN管理` 的结构一致性

## 7.2 列表页能力

### 必需字段

- 调拨单号
- 创建时间
- 线路或来源 -> 去向
- JOB
- 订单号/运单号
- 重量Kg
- 件数
- 物流状态
- 执行状态
- 调拨原因
- 运输方式
- 承运商/司机
- 更新日期

### 必需筛选

- 关键字：调拨单号 / JOB / 订单号 / 运单号
- 线路/来源站/目标站
- 物流状态
- 执行状态
- 业务线
- 日期区间

### 必需动作

- 创建调拨单
- 绑定货物/运单
- 执行
- 确认到达
- 确认入库
- 打印
- 查看详情

## 7.3 新增/编辑调拨单

### 共模字段

- 业务线
- 源仓库
- 目标仓库
- 调拨方式：按订单 / 按集装号
- 选择货物
- 总重量
- 总件数
- 执行日期
- 运输方式
- 承运商/物流公司
- 调拨原因
- 备注

### 起运侧保留字段

- 装箱号
- 发货方式：直接发货 / 先送总仓

### 与 DPN 对齐的扩展字段

- 查询电话
- 司机名称
- 司机电话
- 车牌

说明：

- 上述扩展字段不是所有起运调拨都必须强制填写，但应纳入统一表单能力。
- 这样起运调拨就能覆盖“普通仓间转移”和“类似 DPN 的调度执行”两种场景。

## 7.4 绑定货物能力

- 起运调拨需要补齐 DPN 已有的 `绑定运单/绑定子单`能力
- 支持两类入口：
  - 从候选列表勾选
  - 扫描/批量粘贴
- 候选对象至少要显示：
  - JOB/站点
  - 运单号
  - 订单号
  - 客户
  - 当前状态
  - 件数
  - 重量
  - 更新时间

## 7.5 执行能力

- 起运调拨执行不应只有状态改字面值，应有独立执行动作
- 执行时至少采集：
  - 司机名称
  - 司机电话
  - 司机账号ID（可选）
  - 出库时间
- 如果保留 DPN 风格，也可补充：
  - 承运商
  - 车牌

## 7.6 到达与入库闭环

- 起运调拨必须保留 `确认到达` 与 `确认入库` 两个独立节点
- 这是起运调拨与当前 DPN 页面最大的流程差异，也是后续共模时必须补齐的一段
- 建议统一主链路为：
  - 草稿
  - 待执行
  - 已发运 / 执行中
  - 已到达
  - 已入库 / 已完成
  - 已取消

## 7.7 详情页/轨迹

- 详情页需要统一展示：
  - 调拨基础信息
  - 货物明细
  - 状态轨迹
  - 执行信息
  - 到达/入库确认信息
- 如果当前页面没有详情入口，属于本轮分析识别出的功能缺口

## 7.8 打印

- 既然 DPN 管理已有 `打印`动作，起运调拨也应补齐
- 打印内容至少包括：
  - 调拨单号
  - 源仓/目标仓
  - 货物清单
  - 重量/件数
  - 司机/车牌
  - 执行日期

## 7.9 费用与财务关联

- 费用主数据已允许 `TRANSFER` 与 `DPN` 两种 relatedType
- 需求上应统一规则：
  - 调拨类费用统一归属“调拨主单”
  - 若短期内不改表结构，可保留 `TRANSFER` 与 `DPN` 并存
  - 长期看应避免同类业务分别挂两种 relatedType

## 7.10 权限与组织边界

- 调拨天然是站点协同对象，必须体现“组织 = 站点”的边界
- 起运仓用户默认只看自己授权仓库/站点发起或接收的调拨
- 到达仓 DPN 也应按站点权限过滤，不应作为独立特例

## 9. 本次分析后的需求判断

### 9.1 应立即确认的需求方向

- `起运国仓调拨记录`要向 `DPN管理`靠拢，而不是相反
- `DPN`在业务上归入“调拨类对象”
- `配送`和`自提`与 `DPN/调拨` 解耦

### 9.2 暂不在本轮直接下结论的技术问题

- 是否把 `transfer_orders` 与 `pod_dpn` 直接合表
- 是否继续保留 `到达国仓储 -> 调拨记录` 这个独立菜单
- 是否把当前 `pod_delivery_task` 重命名为“调拨执行单”

这些属于下一阶段设计问题，不应在需求还未确认前直接拍板。

## 10. 待确认项

- DPN 最终是否只保留到达仓菜单名，而底层统一成通用调拨模型
- 起运调拨执行后，是否也需要像 DPN 一样支持“绑定后再执行”，还是允许创建时一次性完成绑定
- 起运调拨是否要支持收货联系人信息；若存在跨站点人工交接，建议保留
- 到达国仓储下的 `调拨记录` 页面，是否计划取代 DPN，还是只保留作通用调拨入口

## 11. 最终建议

- 需求层面先统一口径：`DPN 是调拨，不是配送`
- 产品层面先统一页面能力：让起运调拨补齐 DPN 的绑定、执行、打印和明细能力
- 设计层面再决定：是做“统一调拨基座 + 起运/到达差异扩展”，还是继续双模型但前台共用交互

当前最合理的下一步，不是直接改代码，而是先按本文结论把“调拨主链路、字段共模、状态共模、菜单职责”确认下来，再进入详细设计。
