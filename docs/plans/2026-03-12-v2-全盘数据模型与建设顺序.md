# V2 全盘数据模型与建设顺序（DB First）

日期：2026-03-12  
适用范围：Web 端全流程重构（海运/空运分线），不复用历史数据，按全新模型建设。

## 1. 目标与约束

1. 目标：先定义统一数据模型，再按业务流打通 API 与页面，保证“数据口径一致 + 流程可追踪 + 端到端可跑通”。
2. 约束：订单详情页沿用现有 UI 布局，只替换数据来源和字段绑定。
3. 业务线：`SEA` 与 `AIR` 作为一级业务上下文，所有核心业务表必须带 `business_line`。
4. ALL 视图：只在财务与分析聚合查询，不写入“ALL”业务数据。

## 2. 统一建模原则

1. 单据主表 + 状态流水表：任何业务状态以流水为准，主表存当前状态与更新时间。
2. 主键策略：统一 `TEXT` 主键（推荐 ULID/雪花），业务单号独立字段并加唯一索引。
3. 枚举策略：关键状态字段使用 `CHECK` 约束，跨模块常量在代码层统一枚举。
4. 金额策略：金额字段统一 `DECIMAL/REAL` + 币种 + 汇率，禁止无币种金额。
5. 审计策略：所有核心表包含 `created_by`, `created_at`, `updated_at`。
6. 关联策略：费用、审核、通知必须可回溯到 `order/sub_order/job/dpn/transfer`。

## 5. 核心数据流向（真实业务）

1. 客户主数据建立：`crm_customer` + 发货档案 + 收件人地址。
2. 创建订单：写 `oms_order` + `oms_order_package_initial`。
3. 拆分子单：写 `oms_sub_order`，同步 `oms_order_status_log`。
4. 起运入库：写 `wms_inbound_order` + `wms_inbound_item` + `wms_stock` + `wms_stock_txn`。
5. 实际信息固化：写 `oms_order_package_actual`（重量、尺寸、体积重、计费重）。
6. 任务与装载：创建 `tms_job`、`tms_shipping_unit`、`tms_job_order_rel`。
7. 出口/进口跟踪：写 `tms_tracking_event`，并回写订单/子单当前状态。
8. 创建 DPN：写 `pod_dpn` + `pod_dpn_item`，后续推进 `pod_delivery_task`。
9. 财务录入：写 `fin_fee`，发起 `wf_instance/wf_task`。
10. 审核通过后支付：写 `fin_payment`，回写费用状态与订单支付状态。

## 7. 建设顺序（真实开发顺序）

### Phase 0：基线冻结

1. 冻结现有页面布局，不再做 UI 结构调整。
2. 创建 `v2` 分支，数据库使用新文件（不兼容旧表）。
3. 输出字段字典（前端字段/API字段/DB字段一一对应）。

### Phase 1：DB First（必须先完成）

1. 落地 `schema_v2_mvp.sql`。
2. 建立建库脚本与最小 seed 脚本。
3. 建立状态机常量（订单/子单/任务/DPN/费用/审核）。

验收标准：
1. 数据库可从 0 初始化成功。
2. 能插入一条订单并联动插入初始包裹、子单、库存、任务、费用、审核记录。

### Phase 2：OMS + WMS Origin

1. 实现订单创建、列表、详情、搜索（服务端筛选）。
2. 实现起运入库、库存状态流转、实际信息写回。

验收标准：
1. 单条订单可以从“待入库”推进到“已入库”。
2. 详情页初始信息和实际信息字段完整可见。

### Phase 3：TMS + 跟踪

1. 实现任务创建、子单绑定、运输单元绑定。
2. 实现出口/进口跟踪节点流转并回写状态。

验收标准：
1. 子单可绑定任务和运输单元。
2. 跟踪节点更新后订单状态可自动推进。

### Phase 4：到达国办/仓 + DPN

1. 实现 DPN 创建、关联子单、配送任务执行与签收。
2. 实现客户通知记录。

验收标准：
1. 子单到达后能形成 DPN 并完成签收闭环。

### Phase 5：财务 + 审核

1. 实现费用录入、审批流、支付确认。
2. 实现应收应付与汇率换算展示。

验收标准：
1. 费用状态从草稿到支付完整闭环。
2. 审批任务可追踪到业务单据。

### Phase 6：采购/退赔/备用金 + 报表

1. 接入采购与退赔流程。
2. 生成利润快照与经营分析基础数据。

## 9. 风险与控制

1. 风险：文档字段同义不同名。  
控制：先做字段字典，任何新字段必须登记字典后开发。

2. 风险：多模块状态定义不一致。  
控制：状态常量中心化，禁止页面自定义状态文本。

3. 风险：先做页面后补数据导致返工。  
控制：严格 DB First，API 契约评审通过后再改页面绑定。

4. 风险：ALL 视图污染业务线数据。  
控制：持久层不允许写 `ALL`，仅查询聚合时使用。
