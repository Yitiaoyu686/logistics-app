# 全系统数据流转梳理（基于业务流程，按当前代码重建）

日期：2026-03-18  
依据：`docs/plans/2026-03-16-全模块建设计划-表单与闭环优先.md` + 当前 `server/client/app` 实际代码  
目标：用“可执行接口与真实状态机”重建数据流转，不依赖历史失效文档。

---

## 1. 结论先行

当前系统存在两条并行数据链路：

1. Legacy 链路（`/api/orders`、`/api/warehouse`、`/api/jobs`、`/api/delivery`、`/api/fees`），数据落在 `logistics.db`。
2. V2 链路（`/api/v2/...`），数据落在 `logistics_v2.db`。

“全系统联调”若跨两条链路混跑，会出现状态不一致与数据不可见。  
建议将闭环联调主线统一到 V2 链路，Legacy 仅保留兼容 App 的存量流程。

## 3. 分阶段数据流转（P2-P6 视角）

## 3.1 P2 OMS 主链（主订单）

写入入口：

1. `POST /api/v2/oms/orders`
2. `PUT /api/v2/oms/orders/:id`
3. `POST /api/v2/oms/orders/:id/approve-return`
4. `POST /api/v2/oms/orders/:id/reject-return`

核心落表：

1. `oms_order`
2. `oms_order_package_initial`
3. `oms_order_status_log`

关键规则：

1. 主单创建默认 `order_status = PENDING_INBOUND`。
2. 主单状态主要由子单聚合函数 `refreshOrderStatusByOrderId` 自动回写。
3. 退单通过：主单 `CANCELLED`，子单批量 `CANCELLED`。
4. 退单驳回：主单恢复 `previous_status`。

## 3.2 P3 起运仓（入库与待匹配）

写入入口：

1. `POST /api/v2/wms/inbounds`
2. `POST /api/v2/wms/unmatched-packages/:id/match`
3. `PUT /api/v2/wms/unmatched-packages/:id`
4. `DELETE /api/v2/wms/unmatched-packages/:id`

核心落表：

1. `wms_inbound_order`
2. `wms_inbound_item`
3. `wms_unmatched_package`
4. `oms_order_package_actual`
5. `wms_stock`
6. `wms_stock_txn`
7. `oms_sub_order`
8. `oms_order`
9. `oms_order_status_log`

关键规则：

1. 有单入库：子单变 `INBOUND`，主单聚合刷新。
2. 无单入库：先落 `wms_unmatched_package(status=PENDING)`。
3. 匹配挂单：`unmatched -> MATCHED`，并创建或更新子单为 `INBOUND`。
4. 删除未匹配包裹：`wms_inbound_item.item_status -> ABNORMAL`。

## 3.3 P4 起运国办（任务与集装）

写入入口：

1. `POST /api/v2/tms/jobs`
2. `POST /api/v2/tms/jobs/:id/bind-sub-orders`
3. `POST /api/v2/tms/tracking-events`

核心落表：

1. `tms_job`
2. `tms_shipping_unit`
3. `tms_job_order_rel`
4. `oms_sub_order`
5. `oms_order`
6. `tms_tracking_event`
7. `oms_order_status_log`

关键规则：

1. 任务创建：`job_status = PLANNED`，`current_phase = ORIGIN`。
2. 绑定子单：子单状态置 `PENDING_DEPARTURE`，写状态日志，主单聚合刷新。
3. 跟踪事件可直接驱动子单/主单/任务状态更新（受合法状态集合约束）。

## 3.4 P5 到达国办仓（DPN 与签收）

写入入口：

1. `POST /api/v2/pod/dpns`
2. `POST /api/v2/pod/delivery-tasks`
3. `POST /api/v2/pod/delivery-tasks/:id/sign`

核心落表：

1. `pod_dpn`
2. `pod_dpn_item`
3. `pod_delivery_task`
4. `oms_sub_order`
5. `oms_order`

关键规则：

1. 创建 DPN：关联子单后，子单状态置 `PENDING_DELIVERY`。
2. 创建配送任务：`pod_dpn.dpn_status = ASSIGNED`。
3. 签收：任务 `SIGNED`，DPN `SIGNED`，关联子单全量 `DELIVERED`，主单聚合刷新。

## 3.5 P6 财务与审核闭环

写入入口：

1. `POST /api/v2/finance/fees`
2. `POST /api/v2/workflow/instances`
3. `POST /api/v2/workflow/tasks/:id/action`
4. `POST /api/v2/finance/payments/confirm`

核心落表：

1. `fin_fee`
2. `wf_instance`
3. `wf_task`
4. `fin_payment`
5. `oms_order`

关键规则：

1. 费用创建默认 `fin_fee.fee_status = DRAFT`。
2. 发起审批后费用变 `PENDING_APPROVAL`。
3. 审批动作驱动费用 `APPROVED/REJECTED`。
4. 收款确认后费用 `PAID/PARTIAL_PAID`；若为订单应收同步回写 `oms_order.total_paid_amount` 与 `payment_status`。

## 4. 实体状态机（当前代码口径）

## 4.1 OMS 主单 `oms_order.order_status`

状态集合：

1. `DRAFT`
2. `PENDING_INBOUND`
3. `INBOUND`
4. `PENDING_DEPARTURE`
5. `DEPARTED`
6. `IN_TRANSIT`
7. `ARRIVED`
8. `PARTIAL_DELIVERED`
9. `COMPLETED`
10. `EXCEPTION`
11. `RETURN_APPLIED`
12. `CANCELLED`

主要触发：

1. 入库/匹配/绑定/签收后通过 `refreshOrderStatusByOrderId` 聚合更新。
2. `POST /api/v2/oms/orders/:id/approve-return` 直接置 `CANCELLED`。
3. `POST /api/v2/tms/tracking-events` 可按事件直接更新合法主单状态。

## 4.2 OMS 子单 `oms_sub_order.sub_status`

状态集合：

1. `PENDING_INBOUND`
2. `INBOUND`
3. `PENDING_PACKING`
4. `PACKED`
5. `PENDING_DEPARTURE`
6. `IN_TRANSIT`
7. `CUSTOMS_CLEARANCE`
8. `ARRIVED`
9. `PENDING_DELIVERY`
10. `DELIVERING`
11. `DELIVERED`
12. `EXCEPTION`
13. `RETURN_APPLIED`
14. `CANCELLED`

主要触发：

1. 入库/待匹配挂单：`INBOUND`
2. 绑定任务：`PENDING_DEPARTURE`
3. 跟踪事件：可推进到运输链路各状态
4. 创建 DPN：`PENDING_DELIVERY`
5. 配送签收：`DELIVERED`
6. 退单通过：`CANCELLED`

## 4.3 待匹配包裹 `wms_unmatched_package.status`

状态集合：

1. `PENDING`
2. `MATCHED`
3. `CLOSED`

主要触发：

1. 无单入库生成 `PENDING`
2. 挂单匹配成功置 `MATCHED`
3. 人工关闭置 `CLOSED`

## 4.4 TMS 任务 `tms_job.job_status`

状态集合：

1. `PLANNED`
2. `IN_PROGRESS`
3. `DEPARTED`
4. `IN_TRANSIT`
5. `ARRIVED`
6. `CLEARED`
7. `COMPLETED`
8. `CANCELLED`

主要触发：

1. 任务创建默认 `PLANNED`
2. 跟踪事件可推进任务状态

## 4.5 DPN 与配送

## 5. 数据一致性约束（联调必须检查）

1. 主子一致性：`oms_order.order_status` 必须等于子单聚合结果。
2. 包裹一致性：`oms_order_package_actual.sub_order_id` 必须可追溯到目标子单。
3. 入库一致性：有单入库时必须同时存在 `wms_inbound_item + wms_stock + wms_stock_txn`。
4. 待匹配一致性：`wms_unmatched_package.status=MATCHED` 时必须有 `matched_order_id/matched_sub_order_id`。
5. 任务一致性：`tms_job_order_rel` 关联的子单，其 `job_id` 与关系表 `job_id` 一致。
6. DPN 一致性：`pod_dpn_item` 涉及子单在创建 DPN 后应为 `PENDING_DELIVERY`。
7. 签收一致性：配送签收后，DPN=SIGNED、任务=SIGNED、子单=DELIVERED 同步成立。
8. 财务一致性：`finance/payments/confirm` 后 `fin_fee` 状态应变为 `PAID/PARTIAL_PAID`。
9. 应收一致性：订单级应收收款后，`oms_order.payment_status` 与累计已收金额一致。

## 6. 兼容链路说明（Legacy）

当前 App 与部分 Web 页面仍在调用 Legacy API（`/api/orders/*`、`/api/warehouse/*`、`/api/jobs/*`、`/api/delivery/*`、`/api/fees/*`）。  
Legacy 的状态机与 V2 相似，但数据不在同一库，不会自动互相同步。

建议：

1. 闭环联调时明确“本次走 V2 还是 Legacy”，单次只选一条链路。
2. 若要“全系统一套事实源”，优先把 App 写接口逐步迁到 `/api/v2/*`。

## 7. 当前可执行的联调口径（建议）

1. 先以 V2 打通端到端闭环（OMS -> WMS -> TMS -> POD -> Finance）。
2. 再做 Legacy 与 V2 的迁移映射，不做“双写并跑”。
3. 将一致性检查固化为脚本，至少覆盖第 5 章的 9 条约束。
