# 订单-任务-集装与角色协同规则确认版

日期：2026-03-16  
状态：已根据业务方答复确认（用于 Web 重构落地）

## 1. 文档目的

本文件用于固化以下核心问题：

1. 订单、任务、集装号、包裹、DPN 的真实业务关系。
2. 海运/空运在流程与数据上的隔离边界。
3. 仓库、办公室、销售、财务、管理员的职责和操作权限。
4. 后续表结构、接口、页面联调的统一业务口径。

## 2. 已确认业务规则（逐条落地）

1. 海运与空运完全独立，不能混合。
2. 一个任务可对应多个集装号，集装号不能跨任务复用。
3. 子订单不一定只在一个集装号中（可被拆分到多个集装单元）。
4. 下单先生成主订单，主订单当下可无实货绑定。
5. 仓库按收货先后处理：每次收货一个包裹，创建一个新的子订单，挂在主订单下（1包裹=1子订单）。
6. 一个订单会包含多个货物，执行层按子订单推进；主订单货物信息为子订单货物汇总镜像，不作为独立执行层。
7. 无订单快递先进入待匹配池，后续再匹配到订单。
8. 站点进度更新由仓库和办公室共同参与，办公室为主，仓库主要负责入库/出库节点。
9. 收货、集装、配送首尾环节由仓库执行；发运、清关/报关等中段环节由办公室执行。
10. 路线模板在任务中允许增删改，但仅管理员可操作。
11. 费用会在多环节产生（入库、出库、打包、任务执行等）；起运/到达仓管与办公室可提报增减，最终需财务审核确认。
12. 配送信息关联子订单；DPN 关联子订单。
13. 全部包裹签收是最终完成条件。
14. 异常按子订单记录，并进入审核确认。
15. 仅客户编号要求短码；其他单号采用系统自动生成长编号。
16. 子订单跨集装号时，按订单计费口径分摊（按重量计费则按重量分摊，按体积计费则按体积分摊）。
17. 待匹配池支持创建订单时的推荐匹配能力。
18. 待匹配池匹配权限为仓管、办公室、管理员。
19. 异常审核主体为办公室与财务。
20. 费用流程为“业务提报 -> 销售沟通 -> 财务核对审核”。
21. 物流节点支持自定义；系统先提供常规国际物流默认节点模板。

## 3. 统一实体关系模型（确认口径）

1. `MasterOrder`：客户下单主单，承载客户维度、结算汇总、总状态。
2. `SubOrder`：实际履约执行单元，按仓库收货事件持续生成。
3. `InboundPackage`：三方快递包裹（运单级），可驱动生成/绑定子订单。
4. `ShippingUnit(集装号)`：仓库二次集装单元，可关联多个子订单。
5. `Job(物流任务)`：办公室创建，承接订舱/订板位后的执行主线。
6. `DPN/Delivery`：到达国配送执行实体，直接挂子订单。
7. `Exception`：子订单级异常（缺货/破损/丢失等），需审核。

关系约束：

1. Job:ShippingUnit = 1:N。
2. ShippingUnit:SubOrder = N:M（子订单可跨多个集装单元）。
3. MasterOrder:SubOrder = 1:N。
4. InboundPackage:SubOrder = 1:1（按“每次收货创建子订单”口径）。
5. DPN:SubOrder = N:M（一个 DPN 可配送多个子订单，一个子订单可拆分配送）。

## 4. 端到端流程（执行顺序）

### 4.1 任务预置（办公室）

1. 办公室订舱（海运）或订板位（空运）。
2. 创建 Job（明确业务线、路线模板、站点节点）。
3. Job 下创建/绑定多个集装号（未装货也可先建）。

### 4.2 下单与入库（销售/仓库）

1. 客户下单生成 MasterOrder。
2. 若有包裹先到仓：仓库收货入库，生成 InboundPackage。
3. 每次收货创建新的 SubOrder 并关联 MasterOrder。
4. 无订单包裹进入待匹配池，后续人工/规则匹配到 MasterOrder。

### 4.3 集装与任务推进（仓库/办公室）

1. 仓库按计划把多个子订单装入一个或多个集装号。
2. 集装号绑定到 Job，形成运输执行单元。
3. 办公室推进发运、清关、报关等中段节点。
4. 仓库仅负责入库/出库和首尾操作节点更新。

### 4.4 到达与签收（到达仓/配送）

1. 到达仓处理到港入库与 DPN 入库。
2. 生成/执行配送任务，配送信息回写子订单。
3. 全部包裹签收后，主订单才可最终完成。

### 4.5 费用与异常（全程）

1. 多环节可新增/调整费用（仓管、办公室提报）。
2. 费用变更需销售沟通客户（业务动作），财务审核后生效（系统动作）。
3. 异常按子订单建档并进入审核流程。
4. 异常完成闭环需覆盖拒收、丢失、部分签收补签等场景。

## 5. 角色职责与权限矩阵

1. 销售：客户下单、费用沟通、客户侧反馈，不直接推进中段物流节点。
2. 起运仓管：收货入库、集装、出库、无订单包裹待匹配处理。
3. 到达仓管：到达入库、DPN 入库、配送首尾环节。
4. 起运办公室：任务创建、发运节点推进、清关/报关协同。
5. 到达办公室：进口跟踪、通知客户、到达侧中段推进。
6. 财务：费用审核确认、应收应付确认。
7. 管理员：路线模板与任务节点的增删改授权。
8. 异常审核：办公室初审/复核，财务确认对账与费用影响。

## 6. Web 与数据落地要求（实施约束）

1. 菜单和接口必须按 `businessLine=SEA|AIR` 强隔离。
2. 任务、集装、子订单、DPN、费用、异常都必须带业务线字段。
3. 站点数据权限必须按“组织=站点”做可见域控制。
4. 无订单快递模块必须独立待匹配池，不得直接落入订单明细。
5. 订单详情页展示按主单汇总 + 子单执行明细分层。
6. 费用模块支持“提报-审核-生效”链路，不允许直接跳过审核落账。
7. 待匹配池需要在创建订单/挂单操作时提供推荐匹配（客户、联系方式、历史收件人等维度）。
8. 节点模板内置海运/空运常规模板，并允许管理员在任务中做定制调整。
9. 主单、子单、任务、集装号、入库单、DPN等编号统一系统自动生成（非短码）。

## 7. 本版确认结论

1. 当前规则已完成关键口径确认，可直接进入数据库与接口设计阶段。
2. 无阻塞项；若后续出现新场景，按“子订单执行层优先、主订单汇总层兜底”原则扩展。
