# 2026-03-21 起运国办 JOB 成本模块梳理与优化需求分析

## 1. 分析范围

本次仅分析 Web 端 `海运业务 / 起运国办 / JOB成本` 模块，目标是梳理“JOB 成本录入”从录入、提交到主管审核的真实业务需求，并明确当前实现与客户口径的差距。

本轮范围按用户最新口径收敛为：

1. 只做前端页面 Demo；
2. 只要求页面流程与展示正确；
3. 使用 mock 数据；
4. 不做财务审核链；
5. 不要求本轮打通后端持久化。

## 3. 结论先行

当前 `JOB成本` 不是客户要的“任务成本录入单”，而是一个基于 `fee_records` 的“单条费用台账页面”。

客户当前口径下，`起运国办 / JOB成本` 应改造成：

1. 以 `JOB` 为主业务对象的“成本录入批次”页面，而不是单条费用列表页。
2. 一次录入可包含多条费用明细。
3. 同一个 `JOB` 在生命周期内可发起多次成本录入批次。
4. 提交后进入“主管审核”，不是当前这种单条费用直接审批。
5. 每条费用需要支持不同归属层级：
   - `JOB` 公摊
   - `集装箱号` 公摊
   - `订单号`
   - `子单号`
6. 审核链只保留“主管审核”，不增加财务审核节点。

换句话说，这个模块需要从“费用记录 CRUD”升级为“成本批次 + 费用明细 + 主管审核”的前端页面模型。

## 5. 客户确认的目标业务逻辑

### 5.1 一个任务的成本会多次发生

`docs/meeting-notes.md` 在 2026-03-20 明确写到：

- `成本类型：涉及任务成本、订单成本、COB成本等，可能产生多次，由系统自动按订单分摊`

这说明：

1. 成本不是一次性录完；
2. 同一个任务在不同阶段可以重复发起成本录入；
3. 后续需要支持分摊。

### 5.2 一次录入不是一条费用，而是一批费用

`docs/meeting-notes.md` 明确写到：

- `多个费用提交`

`docs/excel-起运国办.md` 的 `JOB成本录入 POL 2022.xlsx` 中，`录入 收起 / 录入 展开` 页都展示了成组的 `应付明细` 行：

- `供应商`
- `订单号`
- `项目`
- `单价CNY`
- `数量`
- `小计CNY`
- `支付状态`
- `支付途径/日期`
- `审核状态/日期`

并且一页里可同时录入 12 行以上费用。

这说明客户要的“录入”单位是：

- 一张 `JOB成本录入单`
- 其中包含多条 `费用明细`

不是当前页面的“点一次新增，录一条费用”。

### 5.3 审核是主管审核，不是当前的通用单条审批

`docs/meeting-notes.md` 明确写到：

- `主管审核，通知操作员，通知账务`

`docs/excel-审核管理.md` 的 `成本审核POL 2022.xlsx` 也明确体现：

- 审核页底部存在 `主管审核`
- 每条应付明细行支持 `通过 / 驳回`

本轮用户又补充并明确：

- `由仓库主管审核`
- `这个审核跟财务没关系，不需要财务审核`

因此本轮可落的需求口径是：

1. 提交人：起运国办/操作员
2. 审核人：仓库主管
3. 审核链只保留单层主管审核
4. 审核通过后可通知操作员；账务若有需要，仅作为后续通知对象，不是审核节点

### 5.4 费用归属层级不能只有 JOB

`docs/meeting-notes.md` 明确写到：

- `费用可关联，job（公摊），集装箱号（公摊），订单号，子单号`

这说明每条成本明细至少要支持 4 种归属层级：

1. `JOB`
2. `集装箱号`
3. `订单号`
4. `子单号`

其中 `JOB` 与 `集装箱号` 明确带有公摊语义。

### 5.5 本轮实现边界

本轮页面优化明确不包含：

1. 财务审核节点；
2. 财务支付流程；
3. 后端真实流转打通。

本轮只要求把 `录入批次 -> 多条明细 -> 提交主管审核 -> 通过/驳回 -> 重提` 这条前端 Demo 流程做对。

## 6. 当前实现与目标需求的差距

## 6.1 页面模型差距

当前页面：

- 列表主键是“费用记录”
- 新增动作是“新增费用”
- 详情视角是“同 JOB 下费用记录聚合”

目标页面：

- 列表主键应是“JOB 成本录入批次”或“JOB 成本单”
- 新增动作应是“新增成本录入批次”
- 详情视角应是“批次头 + 多条费用明细 + 审核结果”

## 6.2 录入能力差距

当前只支持：

- 单次新增一条费用

目标需要支持：

1. 一次新增多条费用明细；
2. 每条明细可单独选择归属层级；
3. 每条明细可选供应商、费用项目、单价、数量、小计；
4. 同一个 JOB 可重复新增多批次；
5. 批次内需要保存草稿与统一提交。

## 6.3 审核能力差距

当前只支持：

- 单条费用审批
- 被错误并入通用财务审批弹窗

目标需要支持：

1. 主管审核的是“成本录入批次”；
2. 批次内可逐行通过/驳回，或给出整批结论；
3. 审核结果要回写到每条费用明细；
4. 审核后需要回写结果并通知操作员；
5. 被驳回后支持重新编辑并再次提交。

## 6.4 关联层级差距

当前后端 `fee_records.relatedType` 仅能表达单条费用关联到：

- `ORDER`
- `JOB`
- `UNIT`
- `TRANSFER`
- `DPN`

但它不能直接表达以下业务能力：

1. 一张成本单内同时存在多种归属层级；
2. `集装箱号公摊` 的独立口径；
3. 一次录入的多条明细属于同一个提交批次；
4. 一个批次的统一审核状态与提交流程。

## 6.5 数据结构差距

当前 `fee_records` 表是一条记录一条费用，字段集中在：

- 关联对象
- 费用类型
- 金额
- 币种
- 审批状态
- 支付字段

缺少的核心能力包括：

1. 批次头实体；
2. 批次号；
3. 批次提交人/提交时间；
4. 批次审核人/审核时间；
5. 明细归属层级；
6. 公摊规则与分摊结果；
7. 同一 JOB 的多次录入版本。

## 7. 对起运国办 JOB 成本模块的优化需求清单

### 7.1 菜单职责

`起运国办 / JOB成本` 的职责应收敛为：

1. 基于 `JOB` 查看成本录入情况；
2. 为某个 `JOB` 新建成本录入批次；
3. 在批次内维护多条费用明细；
4. 提交主管审核；
5. 查看审核结果。

不应继续把它做成通用费用总账页。

### 7.2 列表页能力

列表页建议从“费用记录列表”改为“JOB 成本批次列表”。

列表至少应支持：

1. 查询条件：
   - JOB
   - 提单号
   - 起运港
   - 目的港
   - 承运人
   - 批次状态
   - 支付状态（若保留则先做 mock 只读）
   - 日期范围
2. 统计卡：
   - 成本批次数
   - 待提交
   - 待主管审核
   - 部分驳回
   - 已审核
   - 已支付/部分支付（若保留则先做 mock 展示）
3. 列表字段：
   - 批次号
   - 站点/JOB
   - 线路
   - 类型
   - 承运人
   - 提单号
   - 起运港
   - 目的港
   - 重量kg
   - 件数
   - 应付合计
   - 支付状态（若保留则先做 mock 展示）
   - 审核状态
   - 最近提交时间
   - 操作
4. 操作：
   - 录入
   - 查看
   - 编辑草稿
   - 再次录入
   - 查看审核意见
   - 查看审核情况

### 7.3 录入页能力

录入页应以“批次表单”形式组织，而不是简单弹窗。

建议结构：

1. `工单详情区`
   - 服务类型
   - 提单号
   - 承运人
   - 件数
   - 提单重量
   - 订单重量
   - 起运港
   - 目的港
   - 离库/离港/到港日期
2. `JOB/站点分摊概览区`
   - 站点
   - JOB
   - 订单数量
   - 件数
   - 重量
   - 重量占比
   - 应收占比
   - 应付占比
   - 收回比例
3. `费用明细区`
   - 明细行可新增多条
   - 每行至少包含：
     - 归属层级
     - 归属对象
     - 供应商
     - 项目
     - 单价
     - 数量
     - 小计
     - 币种
     - 备注
     - 支付状态（可先做 mock 展示）
     - 审核状态
4. 底部动作：
   - 返回
   - 保存草稿
   - 提交审核

### 7.4 多次录入规则

同一 `JOB` 需要支持多次录入，规则建议为：

1. 每次点击“新增录入”产生一个独立批次；
2. 每个批次有自己的状态、提交时间、审核记录；
3. 同一 JOB 可并存多批次，但待审核批次是否允许并存，需要二次确认；
4. JOB 总应付金额由所有有效批次汇总得到。

### 7.5 审核页能力

审核应从“单条费用审批弹窗”改为“成本批次审核页/抽屉”。

至少需要：

1. 展示工单详情；
2. 展示批次内所有费用明细；
3. 每行支持 `通过 / 驳回`；
4. 支持填写整批审核意见；
5. 支持整批提交审核结论；
6. 审核通过后通知操作员；
7. 驳回后允许录入人再次编辑并重提。

### 7.6 本轮实现边界

本轮前端 Demo 明确不做：

1. 财务审核节点；
2. 财务支付流程；
3. 后端持久化打通。

本轮只需要把 `录入批次 -> 多条明细 -> 提交主管审核 -> 通过/驳回 -> 重提` 这条页面流程做对。

## 10. 风险与待确认项

### 10.1 已明确风险

1. 当前 `JOB成本` 页面是单条费用结构，直接小修字段仍无法支撑批次流程。
2. 当前审批入口被并入通用财务审批页，若不重做前端状态模型，主管审核仍会停留在“逐条审批”。
3. `JOB成本` 页面详情里任务基础信息读取当前就有失败，说明 Demo 里任务概览最好也先改成 mock 数据联动。

### 10.2 待二次确认项

1. 同一 JOB 是否允许多个“待审核”批次同时存在。
2. 主管审核时是“逐条必选通过/驳回”，还是允许“整批通过 + 个别驳回”。
3. `集装箱号公摊` 的具体分摊规则：
   - 按重量
   - 按件数
   - 按订单金额
   - 手工指定
4. 被驳回后是原批次回退重编，还是自动生成新版本批次。
5. 页面是否保留“支付状态”展示，还是本轮先隐藏为只读字段。

## 11. 本次分析结论

起运国办 `JOB成本` 模块的核心问题，不是页面字段少，而是业务建模错位。

当前实现把它做成了“通用费用记录页”，而客户真实要的是“JOB 成本录入批次”：

1. 一个 JOB 可多次录入；
2. 一次录入包含多条费用；
3. 每条费用可挂 JOB/集装箱号/订单/子单号；
4. 提交后由主管审核；
5. 审核通过后结束于当前页面状态闭环，不继续进入财务审核。

因此后续优化不应只做表单字段增减，而应按“批次头 + 费用明细 + 单层主管审核”的前端 Demo 整体改造。
