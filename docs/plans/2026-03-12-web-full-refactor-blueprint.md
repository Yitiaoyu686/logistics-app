## 2. 当前状态评估（As-Is）

### 2.1 现有优势

- 核心 API 基础较完整：订单、任务、仓储、配送、费用、客户、认证、通知等已具备。
- 数据模型已具备关键运输字段（`transportType`、route/job/unit 关联关系）。
- 海运端到端 API 流程已有自动化验证（60/60 通过）。
- 多数核心页面已接入真实 API（OMS 列表、起运/到达仓、费用录入/审批、主要 TMS 页面）。

### 2.2 当前阻塞 Web 全流程的关键问题

- 海运/空运上下文仍是全局头部 `Segmented`（`ALL/AIR/SEA`），不是“业务线优先”的架构。
- 起运国办菜单当前只暴露任务列表；出口跟踪、POL 成本、POL 应收、订单费用页面虽存在，但菜单不可达。
- 菜单里的 `oms_order_create` 仍是 `ComingSoon`，真实建单流程藏在订单列表弹窗中。
- 系统设置类页面仍有较多 mock/本地状态实现，后端接口尚未覆盖全部系统域需求。
- 财务/人事部分模块仍是演示态（提成、薪资、备用金核销等未形成完整领域闭环）。
- Excel 里的内容/增长类模块尚未纳入统一 Web 信息架构（服务指南、加盟、推广、工作报告、采购全域流程）。
- 当前构建失败，存在 TS/JSX 语法错误文件：
  - `client/src/pages/oms/SubOrderDetail_new.tsx`
  - `client/src/pages/wms/destination/DestInboundDetail_clean.tsx`

### 2.3 与需求的核心不匹配点

- 需求明确要求海运与空运为两套独立体系，且上下文稳定、列表独立、流程独立。
- 当前 Web 在操作页面仍允许 `ALL` 混合上下文，跨线误操作风险高。

## 3. 目标架构原则

1. 先业务线，后模块。
2. 海运与空运操作上下文完全独立。
3. `ALL` 仅用于分析/财务视角（财务、老板、管理员），不面向一线操作。
4. 列表/详情/新建/编辑全部继承路由业务线上下文，不靠页面内临时筛选。
5. Web 端作为全流程主执行端，App 为扩展端。
6. 共享一套领域模型，但通过策略层强制业务线差异规则（计价、运输单元、校验）。

## 5. 全量功能蓝图（To-Be）

### 5.1 CRM + 面向用户的客户数据

- 公海池、认领/释放流程、私海池。
- 客户档案支持发货人/收货人模板与权限脱敏。
- 收件人目录与用户绑定流程（承接“用户中心 + 我的喵喵”需求）。

### 5.2 OMS（按业务线隔离）

- 海运与空运订单列表按路由上下文独立。
- 支持需求中的高级搜索字段（订单/JOB/集装号/快递号/提单/电话/业务员/币种/服务类型/支付）。
- 创建订单：
  - 空运：普快/特快，按体积重规则计算计费重量。
  - 海运：拼柜/整柜，支持入仓号生成。
- 订单详情采用锚点分区：
  - 基本信息、线路与收发货人、物流状态、初始信息、实际信息、应收明细、发票信息。
- 批量粘贴快递单号与智能解析。

### 5.3 起运仓（按业务线隔离）

- 扫码入库/手动入库，重量与尺寸永久保存。
- 库存按子单粒度展示，并显示未完整入库。
- 未知快递就地建单并绑定客户。
- 运输单元操作：
  - 空运：板货/空运单元装载与封装。
  - 海运：集装箱装载与封箱。
- 调拨流程（站点到站点）。
- 退运/取消操作流程闭环。

### 5.4 起运国办

- 任务/JOB 规划与执行。
- 出口跟踪节点控制（到港、申报、查验、放行、离境）。
- POL 成本录入并进入审核链。
- POL 应收变更与确认支付流程。
- 订单级费用录入。

### 5.5 到达国办

- 进口跟踪节点控制（到港、申报、查验、放行、入库）。
- DPN 创建与分派。
- 客户通知中心。
- POD JOB 成本与 DPN 成本管理。
- POD 应收管理。

### 5.6 到达国仓

- 干线到货入库 + 调拨入库。
- DPN 入库执行与差异核对。
- 库存完整性与可派送状态管理。
- 配送分派、跟踪、签收凭证回传，联动子单/主单状态。

### 5.7 财务 + 审核

- 起运国财务域：
  - JOB 成本支付、TTC、余额报表、利润统计、备用金、奖金、退赔、采购。
- 到达国财务域：
  - DPN/JOB 成本支付、到付余额、TTC、余额报表、利润统计、备用金、资金调拨、退赔、采购。
- 审核中心：
  - 应收审核、POL/POD 成本审核、DPN 成本审核、备用金审核、退赔审核、采购审核。

### 5.8 主数据

- 价格体系：通用价、类别价、服务类型、历史版本、生效窗口。
- 国家/城市/区/站点管理与站点绑定矩阵。
- 基础数据：供应商、物流状态字典、财务项目、费用项目。
- 汇率管理：历史记录与双向换算。

### 5.9 组织与权限

- 权限模板 + 账户管理。
- 员工、部门、岗位、考勤、薪资基础数据。
- 角色 x 业务线 x 模块矩阵权限。

### 5.10 内容与增长

- 服务指南/CMS 内容管理。
- 加盟优势与加盟申请。
- 推广内容发布。
- 工作报告（销售/拜访）。
- 采购申请列表并打通审核与财务支付。

## 6. 海运 vs 空运规则隔离（不可妥协）

### 6.1 必须按业务线区分的能力

- 服务类型选项。
- 计费重量/体积计算规则。
- 运输单元模型。
- 订单与任务表单必填项。
- 路线与价格匹配规则。
- 指标口径（KG 维度 vs CBM 维度）。

### 6.2 界面必须做到业务线隔离

- 路由分根：`/sea/*`、`/air/*`。
- 业务操作页内禁止再放业务线切换器。
- 面包屑必须始终带业务线。

## 7. 重构执行策略

### 阶段 0：稳定基线（1-2 周）

- 修复当前 TypeScript 编译阻塞。
- 冻结菜单 key 与 tab 协议。
- 定义统一路由规范与权限矩阵模型。

### 阶段 1：导航与上下文重构（2 周）

- 取消全局模式切换，改为路由级业务线上下文。
- 菜单重组为“海运/空运优先”。
- 把已存在但不可达页面接入正确菜单（起运国办 + 到达国办链路）。

### 阶段 2：OMS + 起运仓强化（3-4 周）

- 完成 Web 原生建单页面并从菜单直达。
- 强制海运/空运字段与规则校验。
- 打通未知快递、未完整入库、退运/取消操作闭环。

### 阶段 3：TMS + 到达侧闭环（3-4 周）

- 出口/进口全节点流程与可审计节点更新。
- DPN 创建/入库/配送执行，状态自动联动。
- 通知客户模板化与可追溯化。

### 阶段 4：财务与审核闭环（4-5 周）

- 财务按起运/到达两大域拆分落地。
- 替换非 mock 流程（备用金/奖金/采购等）并接入真实域逻辑。
- 审核链与操作日志全量落地。

### 阶段 5：主数据 + 组织权限 + 增长模块（3-4 周）

- 替换剩余 mock 页面，全部改为 API 驱动。
- 完成国家/站点/价格/基础数据治理与 ACL 工具化。

### 阶段 6：验收与迁移（2 周）

- 海运与空运分别执行 UAT 全链路脚本。
- 依据上线清单验收（功能、权限、财务一致性、审计日志）。

## 8. 完成定义（Full Web Flow）

只有同时满足以下条件，才算“Web 全流程跑通”：

1. 一线角色可在 Web 独立完成全动作链，无需回退到 App。
2. 状态流转自动化且可审计（`logistics_records` / 操作日志）。
3. 财务记录可生成、可审批、可核对，且关联链可追踪。
4. 海运与空运数据不能互相误写。
5. 权限校验同时覆盖角色 + 业务线 + 模块边界。
6. 报表可与交易明细逐笔对账。

## 9. 关键风险与控制

- 风险：混合上下文导致数据污染。  
  - 控制：路由级业务线隔离 + 后端按业务线强校验。
- 风险：过渡期导航断裂。  
  - 控制：分阶段双菜单映射与兼容适配层。
- 风险：mock 页面被误判为可上线。  
  - 控制：页面就绪标签（`API_READY`、`MOCK_ONLY`、`BLOCKED`）与发布门禁。
- 风险：财务口径偏差。  
  - 控制：强制对账任务 + 审批链完整性校验。

## 10. 需要立即确认的决策

正式实施前，需要先确定一种执行模式：

- 模式 A：在现有代码库上增量重构（风险更低，但架构清理速度较慢）。
- 模式 B：并行建设领域优先的新版本（`web-v2`），再做受控切换（长期更干净，短期成本更高）。

建议：先走模式 A 完成阶段 0-2，随后基于 OMS + WMS 闭环结果再决定继续增量，还是切换到并行重建。
