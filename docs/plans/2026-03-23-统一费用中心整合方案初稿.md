# 2026-03-23 统一费用中心整合方案初稿

日期：2026-03-23  
范围：围绕全链路物流业务中的成本录入、订单费用录入、应收录入、审核与结算，提出统一整合方案。  
说明：本稿为业务与产品架构方案，优先基于最新业务纪要与现有模块职责梳理，不直接等同于当前代码实现。

## 1. 依据文档

1. `docs/meeting-notes.md`
2. `docs/README-需求分析索引.md`
3. `docs/customer-order-requirements.md`
4. `docs/plans/2026-03-20-物流成本仓配需求影响分析.md`
5. `docs/plans/2026-03-16-订单任务集装与角色协同规则确认版.md`
6. `docs/plans/2026-03-07-system-renovation-design.md`

## 2. 结论先行

不建议把全系统所有费用都做成“一个总页面”。  
更合理的方案是：

`统一底层费用模型 + 分角色业务入口 + 统一审核中心 + 统一结算中心`

也就是说：

1. 业务录入入口保留在各自模块内，符合现有角色习惯。
2. 底层费用单据、费用明细、审核状态、支付状态统一建模。
3. 审核从业务页中抽离，进入统一审核中心。
4. 财务只处理收款、付款、核销、对账，不回到业务页录入原始费用。

## 3. 现有业务事实

### 3.1 费用会在多个环节产生

依据 `docs/meeting-notes.md`：

1. 成本类型涉及任务成本、订单成本、COB 成本等。
2. 一个对象可能产生多次费用。
3. 费用支持多个费用一起提交。
4. 费用可关联：
   - `JOB（公摊）`
   - `集装箱号（公摊）`
   - `订单号`
   - `子单号`

### 3.2 不同环节由不同角色操作

依据 `docs/plans/2026-03-16-订单任务集装与角色协同规则确认版.md`：

1. 办公室创建任务，仓库执行任务。
2. 仓库负责首尾节点，如入库、出库、装卸、配送首尾。
3. 办公室负责中段节点，如发运、清关、报关、调度。
4. 起运/到达仓管与办公室都可能提报费用。
5. 审核、财务、异常确认又是后续独立角色。

### 3.3 当前模块职责已经天然分散

依据 `docs/README-需求分析索引.md` 与 `docs/plans/2026-03-07-system-renovation-design.md`：

1. 起运国办已有：
   - `JOB成本录入`
   - `订单费用`
   - `应收管理`
2. 到达国办已有：
   - `JOB成本录入POD`
   - `DPN成本`
   - `应收管理`
   - 最新纪要又补充了 `订单费用`
3. 财务中心已有：
   - 成本支付
   - 应收收款/应收管理相关能力
4. 审核管理本来就应是独立大模块。

## 4. 为什么不能简单做成一个大页面

如果直接把所有成本、应收、订单费用、DPN费用都塞进一个页面，会产生以下问题：

1. 录入对象层级不同：
   - 有的是 `JOB`
   - 有的是 `DPN`
   - 有的是 `订单`
   - 有的是 `子单`
   - 有的是 `集装号`
2. 操作角色不同：
   - 仓库
   - 起运国办
   - 到达国办
   - 主管
   - 财务
3. 费用语义不同：
   - 成本
   - 应收
   - 到付
   - 公摊费用
   - 异常调整
4. 状态不同：
   - 录入状态
   - 审核状态
   - 付款状态
   - 收款状态
   - 变更状态

因此，页面入口必须分开，但数据模型应统一。

## 5. 建议的总体架构

建议按四层来设计：

### 5.1 业务录入层

保留在原业务模块中，面向业务操作员。

建议保留的入口：

1. 起运国办
   - `JOB成本`
   - `订单费用`
   - `应收管理`
2. 到达国办
   - `JOB成本`
   - `DPN成本`
   - `订单费用`
   - `应收管理`
3. 仓库侧
   - `费用提报`
   - 仅限仓储/装卸/异常类费用

### 5.2 审核中心

从业务页面抽离，集中承接待审单据。

建议按业务类型分池：

1. `成本审核POL`
2. `成本审核POD`
3. `DPN成本审核`
4. `应收审核`
5. 后续可扩：
   - `异常赔付审核`
   - `备用金审核`
   - `采购审核`

### 5.3 结算中心

只由财务使用，承接审核通过的单据。

建议拆成：

1. `成本支付`
2. `应收收款`
3. `核销对账`

### 5.4 分析与报表层

使用统一费用模型聚合出：

1. 成本结构分析
2. 订单利润分析
3. 应收账龄
4. 已付未付
5. 已收未收
6. 站点成本报表

## 6. 统一底层数据模型建议

建议统一成两层主模型：

### 6.1 费用主单 `fee_document`

一张业务费用单据。

建议核心字段：

1. `docNo`
2. `docType`
   - `COST`
   - `RECEIVABLE`
3. `sceneType`
   - `POL_JOB`
   - `POL_ORDER`
   - `POD_JOB`
   - `POD_ORDER`
   - `DPN`
   - `WAREHOUSE`
4. `businessLine`
   - `SEA`
   - `AIR`
5. `phase`
   - `ORIGIN_WAREHOUSE`
   - `ORIGIN_OFFICE`
   - `DEST_OFFICE`
   - `DEST_WAREHOUSE`
   - `DELIVERY`
6. `orgId`
7. `siteId`
8. `relatedEntityType`
   - `JOB`
   - `DPN`
   - `SHIPPING_UNIT`
   - `ORDER`
   - `SUB_ORDER`
9. `relatedEntityNo`
10. `status`
11. `paymentStatus`
12. `submitBatchNo`
13. `createdBy`
14. `submittedBy`
15. `reviewedBy`
16. `financeHandledBy`
17. `createdAt`
18. `updatedAt`

### 6.2 费用明细 `fee_document_item`

一张费用单里的逐条费用行。

建议核心字段：

1. `documentId`
2. `itemNo`
3. `feeType`
4. `feeDirection`
   - `RECEIVABLE`
   - `PAYABLE`
5. `settlementObject`
6. `allocationType`
   - `DIRECT`
   - `SHARED`
7. `allocationTargetType`
   - `JOB`
   - `SHIPPING_UNIT`
   - `ORDER`
   - `SUB_ORDER`
   - `DPN`
8. `allocationTargetNo`
9. `unitPrice`
10. `quantity`
11. `amount`
12. `currency`
13. `remark`
14. `reviewStatus`
15. `reviewComment`
16. `changeSourceItemId`
17. `originalSnapshot`
18. `createdAt`
19. `updatedAt`

### 6.3 变更记录模型

已审核条目不能直接改值，必须发起变更申请。

建议增加：

1. `fee_change_request`
2. `fee_change_request_item`

或者在 `fee_document_item` 中通过：

1. `kind = NORMAL / CHANGE`
2. `changeSourceItemId`
3. `originalSnapshot`

实现版本保留与审核对比。

## 7. 页面整合建议

### 7.1 整合原则

统一交互骨架，但不强行合并成同一页。

统一交互骨架建议为：

1. 顶部统计卡
2. 筛选区
3. 列表一行一张主单据
4. `Drawer` 完成录入、详情、审核
5. 费用条目按表格一行一条录入
6. 已审核条目不可直接改，必须申请修改
7. 后续录入只是在原主单据上追加条目

### 7.2 页面之间真正不同的部分

不同页面只保留以下差异：

1. 绑定对象不同
   - `JOB`
   - `DPN`
   - `ORDER`
2. 费用类型集合不同
3. 详情头部字段不同
4. 审核流程模板不同
5. 角色权限不同

### 7.3 建议的页面族

可统一成 4 个页面族：

1. `对象级成本录入页`
   - JOB成本 POL
   - JOB成本 POD
   - DPN成本
2. `对象级订单费用页`
   - 起运订单费用
   - 到达订单费用
3. `对象级应收页`
   - 起运应收
   - 到达应收
4. `统一审核页`

## 8. 角色与权限边界建议

### 8.1 仓库

可操作：

1. 提报入库费、出库费、装卸费、仓租费、异常处理费
2. 查看自己站点相关费用

不可操作：

1. 终审
2. 付款
3. 应收确认

### 8.2 起运国办

可操作：

1. 起运阶段 `JOB成本`
2. 起运阶段 `订单费用`
3. 起运阶段 `应收管理`

### 8.3 到达国办

可操作：

1. 到达阶段 `JOB成本`
2. `DPN成本`
3. 到达阶段 `订单费用`
4. 到达阶段 `应收管理`

### 8.4 主管

可操作：

1. 审核业务费用
2. 驳回、通过、补充审核意见

### 8.5 财务

可操作：

1. 付款
2. 收款
3. 核销
4. 对账
5. 财务复核类流程

### 8.6 销售

可操作：

1. 查看订单费用与应收结果
2. 参与客户沟通
3. 不建议直接承担全部成本录入职责

## 9. 审核流建议

### 9.1 当前已确认口径

依据 `docs/meeting-notes.md`：

1. 主管审核
2. 通知操作员
3. 通知账务

### 9.2 已存在文档冲突

依据 `docs/plans/2026-03-16-订单任务集装与角色协同规则确认版.md`：

1. 有“最终需财务审核确认”的表述
2. 也有“业务提报 -> 销售沟通 -> 财务核对审核”的口径

### 9.3 建议处理方式

不要做成“所有费用都一套固定审批流”，而是按 `sceneType` 配置工作流：

1. 普通成本
   - `业务提报 -> 主管审核 -> 通知财务`
2. 应收变更
   - `业务提报 -> 销售/主管确认 -> 财务收款处理`
3. 高风险费用或异常赔付
   - `业务提报 -> 主管审核 -> 财务复核`

## 10. 状态模型建议

建议统一拆成三组状态，不要混在一个字段里。

### 10.1 业务单据状态

1. `DRAFT`
2. `PENDING_SUBMIT`
3. `PENDING_REVIEW`
4. `REJECTED`
5. `PART_REJECTED`
6. `APPROVED`

### 10.2 结算状态

成本：

1. `UNPAID`
2. `PARTIAL`
3. `PAID`

应收：

1. `UNRECEIVED`
2. `PARTIAL_RECEIVED`
3. `RECEIVED`

### 10.3 变更状态

1. `NO_CHANGE`
2. `CHANGE_DRAFT`
3. `CHANGE_PENDING`
4. `CHANGE_APPROVED`
5. `CHANGE_REJECTED`

## 12. 风险与缺口

### 12.1 已确认风险

1. 旧模块分散建模，后续直接拼接会越来越乱。
2. 如果不统一状态模型，审核与支付很难贯通。
3. 如果不单独建设审核中心，审批逻辑会继续散落在业务页弹窗中。

### 12.2 当前缺口

1. `集装箱号公摊` 的分摊规则还未最终确认：
   - 按重量
   - 按体积
   - 按件数
   - 可配置
2. `到达国办订单费用` 的精确业务边界仍需继续确认：
   - 是独立于应收管理
   - 还是应收录入的前置录入页
3. 仓库提报的费用是否全部进入同一审核链，还需明确。
4. 财务是否参与所有费用终审，当前文档仍有冲突。

## 13. 最终建议

最终建议不是“合并页面”，而是“合并底层能力”。

最稳妥的方案是：

1. `入口分角色`
2. `数据模型统一`
3. `审核集中`
4. `结算集中`
5. `报表统一`

这样既能兼容当前业务分工，也能避免后续继续出现：

1. 一个费用在多个模块重复维护
2. 状态不一致
3. 角色越做越乱
4. 财务、业务、审核之间数据断层
